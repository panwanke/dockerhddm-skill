# dockerHDDM runtime

## Version policy & authority ⚠️

This skill's workflows, API notes, parameter bounds, and debugging guidance are
**validated against `hcp4715/hddm:1.1.0`**. Other tags exist and are supported,
but their package versions, API surface, and example paths can differ:

| Tag | Status | Notes |
|-----|--------|-------|
| `hcp4715/hddm:1.1.0` | ✅ default / validated | NumPy 2, ArviZ 1.1, maintained PyMC2/Kabuki/HDDM/ssm forks, DataTree `to_infdata` |
| `hcp4715/hddm:1.0.1` | ⚠️ legacy | older Kabuki/HDDM; some converted notebooks were originally tested here |
| `hcp4715/hddm:latest` / untagged | ⚠️ unpinned | tracks upstream; may drift from 1.1.0 |
| `hddm >= 0.8.0` / `0.8` | ⚠️ compat note | the kabuki fork is compatible with `hddm>=0.8.0`, but unverified here |

**When you use a non-1.1.0 tag and its behavior conflicts with this skill, treat
`1.1.0` as authoritative** and report the discrepancy. The active tag is selected
via `image_tag` in the project-local `env.json` (generated by `init_project.py`,
or pass `--image-tag` to it). `inspect_environment.py` prints the expected tag
and warns on mismatch.

## Runtime contract (1.1.0)

- Image tag: `hcp4715/hddm:1.1.0`
- Python 3.12
- NumPy 2.x
- ArviZ 1.1
- maintained PyMC2, Kabuki, HDDM, and ssm-simulators forks
- amd64 and arm64 images

## Pull the image

Docker Hub:

```bash
docker pull hcp4715/hddm:1.1.0
```

For other tags, replace `1.1.0` with the desired tag (e.g.
`hcp4715/hddm:1.0.1`). Mount the same host project so `env.json`,
`config/`, and `data/` are visible inside the container.

CNB mirror:

```bash
docker pull docker.cnb.cool/dockerhddm_sync/dockerhddm/hcp4715-hddm:1.1.0
docker tag docker.cnb.cool/dockerhddm_sync/dockerhddm/hcp4715-hddm:1.1.0 \
  hcp4715/hddm:1.1.0
```

PowerShell supports `$(pwd)`; `cmd.exe` needs an explicit host path. Quote paths
that contain spaces. Mount the project root, not an anonymous temporary folder,
because `--rm` deletes the container after exit.

## Launch configurations (run 配置矩阵) ⚠️

Every `docker run` below shares the **same skeleton** — you vary a few flags to
match your machine and workflow. Replace these placeholders before running:

- `$PWD` — the project directory you are standing in (expanded by the shell).
- `$DATA_DIR` — any *other* host directory you want visible inside the container
  (e.g. a shared clean-data folder). If you don't need a second volume, drop that
  `-v` line.

### The flags you can change

| Flag | What it does | Example |
|------|--------------|---------|
| `--cpus=N` | Limit how many host CPU cores the container may use. Set `N` to your machine's core count (or fewer) for long MCMC fits; use `--cpus=1` for cheap preflight checks. | `--cpus=32` |
| `-v HOST:CONTAINER` | Bind-mount a host directory into the container. Repeat it to mount **more than one** directory. | `-v "$PWD":/home/jovyan/work` |
| `-w DIR` | Container working directory after start. | `-w /home/jovyan/work` |
| `-p HOST:CONTAINER` | Publish a container port to a host port. Change `HOST` if the default is taken. | `-p 7777:8888` |
| `-it` | Interactive + pseudo-TTY (keep for shells/notebooks). | — |
| `--rm` | Delete the container when it exits. **Files outside a mount are lost.** | — |
| command | What the container runs instead of its default entrypoint: `jupyter notebook`, `bash`, or `bash -lc '...'`. | `bash` |

### Template — interactive, Bash mode (most flexible)

This is the recommended starting point when you want to write and run plain
Python scripts, or when you also need to mount a separate data directory:

```bash
docker run -it --rm \
  --cpus=32 \
  -v "$PWD":/home/jovyan/work \
  -v "$DATA_DIR":/home/jovyan/work/data \
  -w /home/jovyan/work \
  -p 7777:8888 \
  hcp4715/hddm:1.1.0 \
  bash
```

What each part means:

- `--cpus=32` — cap CPU usage at 32 cores. Use your machine's real core count.
- `-v "$PWD":/home/jovyan/work` — your project becomes `/home/jovyan/work`.
- `-v "$DATA_DIR":/home/jovyan/work/data` — a **second** mount: a shared dataset
  folder appears at `/home/jovyan/work/data`. Omit this line if you only need one
  volume. You may add even more `-v` lines the same way.
- `-w /home/jovyan/work` — the shell opens here, so relative paths in your scripts
  resolve against your mounted project.
- `-p 7777:8888` — map host port `7777` to the container's Jupyter port `8888`
  (unused in Bash mode, but harmless; see Mode 1 if you switch to Jupyter).
- trailing `bash` — override the default entrypoint and drop you into a shell
  instead of auto-starting Jupyter.

### Mounting more than one directory

Just repeat `-v`. The first mount is almost always your project root
(`/home/jovyan/work`); additional mounts land at sub-paths you choose
(`/home/jovyan/work/data`, `/home/jovyan/work/figs`, etc.). Everything you write
inside a mounted path persists on the host after `--rm`.

### Custom host port (avoid "port already allocated")

If `8888` (or whatever you pick) is taken, change only the **host** side:

```bash
-p 7777:8888   # host 7777 → container 8888
# then open http://127.0.0.1:7777/...  (see Mode 1)
```

The container side (`8888`) stays fixed because that is where Jupyter listens.

### Preflight — cheap write-permission check

Before a long run, confirm the container can write into your mount. Use one core
and a tiny script:

```bash
docker run --rm --cpus=1 \
  -v "$PWD":/home/jovyan/work \
  -v "$DATA_DIR":/home/jovyan/work/data \
  -w /home/jovyan/work \
  hcp4715/hddm:1.1.0 \
  bash -c 'touch /home/jovyan/work/.write_test && echo OK && rm /home/jovyan/work/.write_test'
```

If you see `OK`, the mount is writable. If the container's `jovyan` user cannot
write, fix host directory permissions (e.g. make the project dir group-writable)
before a real fit — do **not** paste personal absolute paths into shared skill
projects.

### Non-interactive one-shot batch run (server / CI)

Drop `-it` and `-p`, and pass a command with `bash -lc '...'`. The container runs
the script and exits on its own — ideal for headless servers:

```bash
docker run --rm --cpus=32 \
  -v "$PWD":/home/jovyan/work \
  -v "$DATA_DIR":/home/jovyan/work/data \
  -w /home/jovyan/work \
  hcp4715/hddm:1.1.0 \
  bash -lc 'python 3_fitting/fit.py --stage sample'
```

> **Bind-mount execution tip:** some hosts forbid executing a script *from* a
> bind mount (Python can read the file but not run it as code). If you hit that,
> copy the script into the container's writable `/tmp` first, then run it:
> `cp /home/jovyan/work/3_fitting/fit.py /tmp/fit.py && python /tmp/fit.py`.

### Docker daemon permission (optional)

If the container never starts and you see
`permission denied while trying to connect to the docker API at unix:///var/run/docker.sock`,
the issue is host daemon access, not your project. Fix once:

```bash
sudo usermod -aG docker "$USER"   # then log out/in, or run: newgrp docker
docker run --rm hello-world       # verify
```

After this, you can drop `sudo` from the `docker run` commands above. The
`sudo` prefix shown in some older project docs is server-specific and not required
for a normal local setup.

## Two usage modes

dockerHDDM supports two distinct ways of working inside the container. Pick one
per session — they use the **same `docker run` skeleton**, only the trailing
command differs.

### Mode 1 — Jupyter (interactive notebooks)

Use this when you want to explore data, prototype models, and keep an
`.ipynb` notebook.

**1. Launch with the Jupyter command** (note: no trailing `bash` — the command is
`jupyter notebook`, or `jupyter lab`):

```bash
docker run -it --rm \
  -v "$PWD":/home/jovyan/work \
  -p 8888:8888 \
  hcp4715/hddm:1.1.0 \
  jupyter notebook
```

**2. Connect to the kernel.** When the container starts, it prints a startup log
that ends with a line like:

```text
Copy and paste URL: http://127.0.0.1:8888/?token=<long-hex-token>
```

Copy that **entire URL** and open it in your browser. That page is the
dockerHDDM Jupyter kernel — you are now connected.

- If you launched with `-p 7777:8888`, replace the port in the URL:
  `http://127.0.0.1:7777/?token=<long-hex-token>`.
- If port `8888` was already in use, Docker picks another container port; the
  printed URL already reflects the real one — just copy it.
- The token is generated per container; the `?token=jupyter-token` string shown
  in the Pan et al. paper is an illustrative placeholder, not a real token.

**3. Create a notebook.** In the Jupyter UI, click **New → Python 3** (or
**Notebook**). Write your HDDM code there. Anything saved under
`/home/jovyan/work` (your mounted project) persists on the host after the
container stops; anything saved elsewhere inside the container is lost with
`--rm`.

### Mode 2 — Bash (plain Python scripts)

Use this for long fits, reproducible batch jobs, or any headless/server run. You
do **not** need a notebook.

**1. Launch with the trailing `bash`** (the template in the previous section):

```bash
docker run -it --rm \
  --cpus=32 \
  -v "$PWD":/home/jovyan/work \
  -v "$DATA_DIR":/home/jovyan/work/data \
  -w /home/jovyan/work \
  hcp4715/hddm:1.1.0 \
  bash
```

**2. Write and run scripts.** You land in a shell at `/home/jovyan/work`. Create
plain `.py` files on the host (they are mounted) or with `vi`/`cat` inside, then
run them:

```bash
python 3_fitting/fit.py --stage sample --model baseline
```

Your project and data mounts are visible; outputs written into the mounts persist
on the host. For non-interactive execution, use the `bash -lc '...'` one-shot form
shown above instead of an interactive shell.

### Which mode should I use?

| | Mode 1 — Jupyter | Mode 2 — Bash |
|---|---|---|
| Best for | Prototyping, exploration, teaching, keeping a notebook | Long MCMC fits, batch jobs, servers, CI |
| Launched by | `... jupyter notebook` | `... bash` (or `bash -lc '...'`) |
| You write | `.ipynb` notebooks | plain `.py` scripts |
| Connection | Browser URL + token from logs | the container shell prompt |
| Needs `-p` | yes (to reach Jupyter) | optional |

You can remember a default with the project-local `env.json` `default_mode` key
(set by `init_project.py --mode inference|simulation|hybrid`); it does not change
how Docker launches, it only records your intent for the agent.

## Sanity checks & troubleshooting

Both modes fail for a small set of predictable reasons — almost always a missing
flag, a mount/permission mistake, or the container exiting before you connect.
Run these checks in order.

### Before you run — verify the image and Docker daemon

```bash
docker images | grep hcp4715/hddm     # confirm the image is pulled (tag shown)
docker info >/dev/null 2>&1 && echo "daemon OK" || echo "daemon DOWN"
docker run --rm hello-world          # ultimate daemon/permission sanity check
```

- If `docker images` lists nothing for `hcp4715/hddm`, run
  `docker pull hcp4715/hddm:1.1.0`.
- If `docker info` / `hello-world` fails with a permission or "cannot connect to
  the docker API" error, fix daemon access (see the Docker daemon permission note
  in **Launch configurations**).

### After you launch — confirm the container is actually running

Open a **second** terminal and check:

```bash
docker ps        # lists running containers; note the NAMES / CONTAINER ID
```

- Nothing listed? The container exited immediately. Find out why:

  ```bash
  docker ps -a              # find the exited container
  docker logs <CONTAINER_ID>   # shows the real error (bad command, missing mount, etc.)
  ```

- In Jupyter mode the same `docker logs` output is where the `token` URL is
  printed (see below).

### Mode 1 — Jupyter won't open / can't connect

| Symptom | Likely cause | Fix |
|---|---|---|
| Browser "can't reach" / connection refused | forgot `-p HOST:8888`, or used a different host port than the URL | add `-p 8888:8888` (or `-p 7777:8888` and open `http://127.0.0.1:7777/...`) |
| No token URL in logs / Jupyter never started | container exited, or command wasn't `jupyter notebook` | check `docker logs <ID>`; trailing command must be `jupyter notebook` (not `bash`) |
| "Port 8888 is already allocated" | host port taken | use a different host port, e.g. `-p 7777:8888`, and open that port in the URL |
| URL opens but rejects the token | copy-paste truncated the token | copy the **whole** `http://127.0.0.1:PORT/?token=...` line from `docker logs` |
| Token works once then "invalid" | container restarted → new token | re-run `docker logs <ID>` for the fresh token, or relaunch |
| Page loads but no files / wrong directory | mounted the wrong path or forgot `-v` | confirm `-v "$PWD":/home/jovyan/work`; files appear under `/home/jovyan/work` |
| Launched without `-it` | Jupyter needs the attached TTY to stay up | use `-it` for interactive Jupyter |

Retrieve the connection URL at any time:

```bash
docker logs <CONTAINER_ID> 2>&1 | grep -o 'http://127.0.0.1:[0-9]*/?token=[a-f0-9]*'
```

### Mode 2 — Bash can't see / read / run my files

| Symptom | Likely cause | Fix |
|---|---|---|
| `ls` shows nothing / `No such file` | forgot `-v "$PWD":/home/jovyan/work`, or landed in a non-mounted dir | confirm the `-v` line; you should be at `/home/jovyan/work` (`pwd`) |
| Wrong data dir / `data/` missing | second data volume not mounted, or wrong path | add `-v "$DATA_DIR":/home/jovyan/work/data`; it appears at `/home/jovyan/work/data` |
| `Permission denied` on the mount | host dir not writable by the container's `jovyan` user | run the `--cpus=1` write-test in **Launch configurations**; fix host dir perms |
| `can't open file` though it's there | wrong working directory | `cd /home/jovyan/work` or add `-w /home/jovyan/work` |
| `python: can't open file` / "Permission denied" on a script | bind-mount exec restriction (read OK, execute blocked) | copy to `/tmp` first: `cp /home/jovyan/work/3_fitting/fit.py /tmp/fit.py && python /tmp/fit.py` |
| Script errors look like Python syntax but the file is fine | CRLF line endings from a Windows copy | `sed -i 's/\r$//' 3_fitting/*.py` (or `*.bash`) before running |
| Files "disappeared" after exit | wrote outside a mount, with `--rm` | always write under `/home/jovyan/work/...` |
| `command not found: python` / import errors | wrong image tag or container exited | confirm tag `1.1.0`; re-run `inspect_environment.py` |

### Smoke check (verify the Python stack)

Inside the container (either mode):

```bash
python -c "import numpy, arviz, pymc, kabuki, hddm, ssms; \
print(numpy.__version__, arviz.__version__, pymc.__version__, hddm.__version__)"
python /path/to/dockerhddm-skill/scripts/inspect_environment.py
```

Confirm `arviz.loo_subsample`, multi-chain `sample`, and DataTree conversion
before using v1.1-only features.

## Persistence rules

- Host-mounted project: durable.
- Unmounted container filesystem: disposable.
- `models/*.db`: PyMC2 trace database.
- `models/*.hddm`: pickled HDDM model.
- `models/*.nc`: ArviZ/xarray inference artifact.
- Record image tag and submodule commits in the project README or run log.
